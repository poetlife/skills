# 需求验证与评测工作流（Evaluation）

本 reference 定义贯穿项目全生命周期的验证机制：结合 AI 执行任务时，把人对“什么算做对了”的判断**形式化、程序化**为可重复执行的验证资产，使初次交付、对话纠偏、代码重构、需求变更、排障与持续进化都能自动验证，而不需要人类反复充当裁判。

## 核心理念：概念统一，载体灵活

1. **Evaluation 是机制，不是某一种固定测试形态**
   - 只要能程序化地检验需求目标或锁死关键约束，载体可以是**单元测试**、**集成测试**、**黑盒 / E2E / 浏览器校验**、**基准评测集**或**运行期查询脚本**——视任务性质与项目既有测试框架灵活选择，不必强行另起炉灶。
   - 例如：给绘制地图的网页锁死轮廓逻辑，既可以用单元测试锁死轮廓坐标/拓扑计算不变量，也可以用黑盒浏览器校验锁死最终渲染出的轮廓边界，具体选最直接、最稳的载体。
2. **验证目标随生命周期动态生长，不必一次给全**
   - 有些目标在提出需求时就能给全，开工前先形式化、程序化；
   - 有些约束是在**与 AI 对话迭代、纠正它的错误逻辑**时才暴露出来的——核心原则是：**人一旦在对话中纠正了 AI 的逻辑，就把这条约束顺手沉淀成程序化验证锁死**，不要只留在聊天记录里，避免后续改动再次破坏。
3. **人的角色与 AI 的重心**
   - **人**：定义验证目标、在协作中纠偏，把判断标准交给程序；
   - **程序化验证资产**：跨版本、跨对话的自动化裁判；
   - **AI**：既要交付实现，也要交付和维护与目标对齐的可执行验证资产。

```text
目标来源（持续生长）：
  ① 提需求时给定的初始目标
  ② 与 AI 对话中纠正错误逻辑时追加的约束
  ③ 排障（debugging）确认的故障复现条件
  ④ 线上进化（evolution）发现的退化或失败模式
        │
        ▼
1. 形式化：拆解为无歧义判据（L0 静态门禁 / L1 确定性 / L2 评测评分 / L3 最小人工）
        │
        ▼
2. 程序化：选最合适的载体落地（lint·AST·Schema 守门 / 单测 / 集成 / 黑盒 E2E / evals / 运行期脚本）
        │
        ▼
3. 全生命周期闭环：AI 围绕验证自闭环迭代；后续重构自动回归；需求变更同步演化
```

## 核心产物与唯一信源

- `docs/design/<module>.md`：功能行为与验证目标（What & Why）的 SSOT，声明验证契约及对应的可执行入口。
- `docs/evaluation.md`：项目级验证总览与索引（声明本项目实际采用的验证载体、运行命令、结果判读与演进规则）。
- **程序化验证资产**：复用项目既有测试目录（单元测试、集成测试、E2E 测试）及按需建立的 `evals/`（独立黑盒校验、L2 评测集/评分脚本、供 `evolution` 复跑的运行期脚本）。
- `docs/testing.md`：单元测试编写原则（如何把单元测试写好、写稳）。
- `docs/evolution/`：运行期跨周期验证与线上数据闭环，承接离线无法验证的长期/真实流量目标，并将线上异常回流为离线验证用例。

## 1. 收集与对齐验证目标

验证目标可以来自四个时机，不必等“全部想清楚”才开始，但**动代码前至少要有当前这一步的明确目标**：

1. **提需求时前置对齐**：用户提出新功能或大改动时，应尽量带上明确的验证目标；若表述过于模糊（如“优化一下体验”“支持导出”），AI 先提出可检验的目标草案与用户确认。
2. **对话纠偏时即时补齐**：与 AI 协作过程中，每当用户指出“这里逻辑不对 / 这个边界不能破 / 这个轮廓要锁死”，AI 在修正实现的同时，同步把这条纠正补充为一条可执行的验证用例。
3. **排障修复时沉淀复现**：定位到 bug 根因后，先固化复现该缺陷的验证用例，再修代码。
4. **线上进化时回流样本**：`evolution` 发现真实失败模式或退化时，将其脱敏沉淀为离线回归用例。

若需求会改变既有对外契约，先读取入口文件的 `project-stage`，按阶段规则决定能否做破坏性变更。

## 2. 形式化：按可程序化程度分层，按任务选载体

把验证目标拆解为无歧义的验证项（场景/输入、可观测判据或阈值、验证层级、落地载体）。显式分三层，避免“假装一切都能写死断言”或“全靠人眼看”：

| 层级 | 类型 | 适用场景 | 典型载体（视情况选择） |
|------|------|----------|------------------------|
| **L0** | 静态门禁（Static Guardrails） | 格式与导出文档、类型安全、架构分层/导入边界、SSOT 唯一入口守护、并发/上下文/配置红线、协议/Schema 契约、生成物一致性 | 语言 linter + `depguard`/`import-linter` + 自研 AST/Schema 检查器 + `gen-check`（**详见 [static-checks.md](static-checks.md)**，100% 自动阻断） |
| **L1** | 确定性断言（Deterministic） | 算法/几何不变量、接口/CLI 契约、状态与数据一致性、退出码、错误语义、渲染边界、性能硬预算 | 单元测试、集成测试、黑盒 / E2E 脚本、无头浏览器 DOM/SVG 断言（**必须 100% 程序化**） |
| **L2** | 评测与评分（Scored Eval / Rubric） | 非确定性输出、生成/分类质量、检索准确率、Agent 决策与工具调用路径 | `evals/` 固定输入集 + 评分脚本或固定 Rubric Judge + 通过线与基线对比 |
| **L3** | 最小人工核验（Minimal Human Sign-off） | 确实无法客观程序化的主观体验（如整体视觉美感、文案体感） | 极简人工核对清单，明确为何暂无法程序化，并伺机下沉为 L1/L2 |

离线无法覆盖的长期/线上真实流量目标，标记为**运行期验证（Runtime / Evolution）**，绑定可复跑查询命令与观察窗口，上线后交接给 [evolution.md](evolution.md)。

### 载体选择原则

- **共性结构反模式 / 架构与契约红线**（如跨层 import、绕开 SSOT 入口、裸起并发导致 trace 断链、协议禁用浮点、生成物漏同步）→ 优先下沉为 **L0 静态门禁**（linter / 依赖边界 / 自定义 AST·Schema 检查器，见 [static-checks.md](static-checks.md)），一次拦截整类问题。
- **逻辑/规则/不变量本身清晰独立**（如地图轮廓闭合与坐标范围计算、价格/权限规则）→ 优先用**单元测试（L1）**锁死，反馈最快。
- **跨模块协作、持久化、协议或真实产物**（如 API、CLI 输出文件、数据库事务）→ 用**集成测试 / 黑盒验收**锁死，不 mock 核心路径。
- **可视化/交互/黑箱系统**（如网页地图绘制、终端交互、外部程序封装）→ 用**黑盒 E2E / DOM 或 SVG 几何检查 / 快照不变量**锁死关键约束，不强求测全像素，只锁死不能破的逻辑。
- **概率性/AI 行为** → 用**固定数据集 + 可复跑评分脚本**做 L2 评测。

## 3. 程序化落地要点

无论选择哪种载体，程序化验证资产都应满足：

1. **目标优先于实现**：已知的目标先落地验证再写实现；对话中新增的纠偏约束当场补齐验证再确认通过。
2. **锁死真实行为，避免伪验证**：验证应直击目标不变量或真实对外行为，不得用 mock 绕开待验证的核心逻辑，避免只测内部私有细节导致重构就碎。
3. **机器可读、自闭环友好**：
   - `0` 退出码表示通过，非 `0` 表示失败；
   - 失败输出包含目标/用例标识、预期 vs 实际与关键上下文，让 AI 无需人工解释就能直接定位修复；
   - L2 评测输出结构化分项指标与基线对比。
4. **分层可快速运行**：支持按模块/用例快速运行（加速对话迭代），也支持一键全量回归（确保改动无副作用）。

## 4. 全生命周期演进与修改边界

验证资产随项目持续演化，目标是**在不需要人类每次参与判断的前提下，杜绝静默降标**：

| 生命周期场景 | 对既有验证资产的操作规则 | AI 自主权与人类介入点 |
|--------------|--------------------------|------------------------|
| **新功能开发** | 按已对齐目标新增验证（选最合适载体）；既有验证原样运行作为回归护栏 | 目标对齐后，AI 自主补齐验证与实现直到全绿 |
| **对话中纠偏** | 把用户刚纠正的逻辑即时沉淀为新的验证用例，锁死该约束 | AI 自主补齐用例并跑通，防止后续对话改回旧错 |
| **代码重构 / 优化**（需求不变） | 既有验证为**只读裁判**，不得删减断言、放宽阈值或跳过用例 | AI 自主完成，全量绿灯即自动证明未破坏行为，无需人工复判 |
| **需求变更 / 契约调整** | **验证随需求一起演化**：先按 `project-stage` 判断兼容性，再同步更新 `docs/design/` 与受影响的验证用例，最后改实现 | `greenfield`：按新需求自主同步更新；`confirm`：确认破坏性影响面后更新；`compatible`：严禁破坏既有验证，仅可增量扩展 |
| **缺陷修复 / 线上进化** | 先将故障复现条件或线上失败样本沉淀为离线回归用例，再修复并验证 | AI 自主固化回归用例，永久防复发 |

### 绝对红线（全生命周期禁止）

- **禁止无需求依据的降标**：不得为了让代码“变绿”，在没有明确需求变更依据的情况下删除既有验证、跳过失败用例、放宽阈值或 mock 掉核心校验逻辑。
- **禁止口头宣称通过**：交付结论必须附带实际运行过的验证命令与结果摘要。

## 5. 与 Testing、Debugging、Evolution 的衔接

- **与 `docs/testing.md` 的关系**：单元测试本身就是 L1 程序化验证的重要载体之一；`docs/testing.md` 聚焦“如何写好单元测试（小函数、Table Driven、无副作用）”，`docs/evaluation.md` 聚焦“项目的全部需求验证目标分别由哪些载体覆盖、如何运行与演进”。
- **与 `docs/debugging/` 的闭环**：排障定位根因后，在「预防措施」里登记沉淀的回归验证路径（单测、集成或 `evals/`）。
- **与 `docs/evolution/` 的闭环**：离线测不到的运行期目标交接给 `evolution` 用可复跑脚本验证；`evolution` 发现并确认的线上问题，修复时必须回流一条离线回归验证。

## 6. 实战示例

### 示例 A：动态生长 + 多载体混合（网页地图绘制）

一个绘制区域地图的网页应用，验证目标并非一开始就完美列全，而是在「初始约定 + 对话纠偏」中逐步锁死：

1. **初始目标（开工前给定）**
   - 轮廓多边形必须闭合且不能自相交 → 用**单元测试**直接锁死几何校验函数（毫秒级反馈）；
   - 给定 GeoJSON 加载页面后，画布/SVG 必须渲染出对应区域且所有顶点落在视口边界内 → 用**黑盒浏览器测试（Playwright）**读取实际渲染的 SVG path / bounding box 做断言（锁死可视化结果，不依赖人眼每次看图）。
2. **对话中纠偏并即时沉淀**
   - 迭代时发现：用户连续放大 3 倍后，相邻两块区域的共享边界出现缝隙；用户在对话里指出了这个错误逻辑。
   - AI 修复投影/取整逻辑的同时，立刻补一条**单元测试**（验证共享边顶点在不同缩放级别下坐标严格相等）+ 一条**黑盒用例**（模拟缩放 3 倍后断言相邻轮廓间隙 = 0）。从此后续无论怎么改渲染性能或 UI，这条轮廓逻辑都被程序锁死，不需要人再肉眼检查。

### 示例 B：L1 + L2 + 全生命周期闭环（`ticket-triage` 工单分类与周报导出）

1. **需求目标与形式化（`docs/design/ticket-triage.md`）**

| 目标 ID | 分层 | 场景与输入 | 可观测判据 / 通过阈值 | 落地载体 |
|---------|------|------------|------------------------|----------|
| `V-01` | L1 | 标准工单 JSON → 执行导出 CLI | 退出码 `0`；CSV 行数 = 输入数；含 `id,category,created_at`；UTF-8 无乱码 | 集成/黑盒测试 `tests/integration/ticket_export.test.py` |
| `V-02` | L1 | 非法 JSON → 执行导出 CLI | 退出码非 `0`；stderr 含错误定位；不遗留脏文件 | 集成/黑盒测试 `tests/integration/ticket_export.test.py` |
| `V-03` | L2 | 50 条已标注工单集 | 准确率 ≥ 90% 且不低于基线；P95 < 500ms | `evals/benchmarks/triage_accuracy.eval.py` |
| `V-04` | L3 | 抽查 3 份导出 CSV 可读性 | 运营可直接阅读（仅首次上线人工抽检） | 人工抽检清单 |
| `V-05` | 运行期 | 上线后 7 天线上分类日志 | `unknown` 占比 < 5% | `evals/runtime/check_unknown_rate.sh`（交接 `evolution`） |

2. **程序化示例（黑盒验收 + L2 机器可读诊断）**

L1 黑盒验收（调用真实 CLI 产物，不 mock 核心逻辑）：

```python
import csv, json, subprocess, tempfile
from pathlib import Path

def test_v01_valid_export():
    with tempfile.TemporaryDirectory() as tmp:
        inp, out = Path(tmp) / "tickets.json", Path(tmp) / "weekly.csv"
        inp.write_text(json.dumps([
            {"id": "T-1", "text": "发票抬头开错了", "created_at": "2026-11-20"},
            {"id": "T-2", "text": "登录后一直白屏", "created_at": "2026-11-21"},
        ]), encoding="utf-8")

        res = subprocess.run(["ticket-triage", "export", "--in", str(inp), "--out", str(out)],
                             capture_output=True, text=True)
        assert res.returncode == 0, f"V-01 failed: stderr={res.stderr}"
        rows = list(csv.DictReader(out.open(encoding="utf-8")))
        assert len(rows) == 2
        assert {"id", "category", "created_at"}.issubset(rows[0].keys())
```

L2 评测失败时的机器可读输出（非零退出码，Agent 据此直接定位修复，无需人工解读）：

```json
{
  "target_id": "V-03",
  "passed": false,
  "metrics": { "accuracy": 0.86, "baseline": 0.90, "p95_ms": 310 },
  "threshold": { "accuracy_min": 0.90, "p95_ms_max": 500 },
  "failed_samples": [
    { "id": "S-17", "expected": "billing", "actual": "unknown", "text": "invoice PDF 无法下载" },
    { "id": "S-34", "expected": "auth", "actual": "bug", "text": "SSO token expired loop" }
  ]
}
```

3. **后续生命周期演进**
   - **内部重构**：导出改为流式写入或更换模型 → 跑全量验证（`V-01 ~ V-03` 全绿）→ **自动证明未破坏行为，无需人工复判**。
   - **需求变更**（如新增 `priority` 列、空输入改为输出空表头而非报错）：按 `project-stage` 处理兼容性，同步更新 spec 与对应验证用例，再改实现。
   - **线上 Evolution 回流**：上线 7 天后 `evals/runtime/check_unknown_rate.sh` 发现 `unknown` 占比 `8.2%`，定位为日文/表情编码截断 → 将脱敏样本追加进 `triage-dataset.jsonl` 并补一条 L1 回归用例 → 修复通过后，下一周期用同一脚本复验降至 `2.1%` 标记 `validated`。
