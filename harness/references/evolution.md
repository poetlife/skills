# 持续进化工作流

本 reference 定义从事实数据到改进验证的完整循环。只有运行进化分析、创建改进工作项或回看效果时读取。

## 核心产物与唯一信源

```text
事实源 -> 周期报告 -> 候选项 registry -> 需求/缺陷/文档/skill -> 实施（附回归 eval） -> 下一周期程序化验证
            不可变快照          跨周期状态 SSOT                       |                         |
                 ^----------------------------------------------------+-------------------------+
                                  线上失败模式回流 evals/ ，永久防复发
```

- `docs/evolution/reports/<YYYY-MM-DD>-<scope>.md`：一次分析的证据快照。生成后不改写事实；补充内容用勘误说明或新报告。
- `docs/evolution/registry.md`：候选项身份、状态、外部链接、程序化验证入口与结论的唯一信源。报告和外部工作项只链接它，不复制状态。
- `docs/design/`：已接受的功能行为与验证目标 SSOT。
- `docs/evaluation.md` 与项目程序化验证资产（单测、集成测试、黑盒/E2E 或按需建立的 `evals/`）：承载 `evolution` 回流的离线回归用例与可复跑的线上验证脚本，规范见 [evaluation.md](evaluation.md)。
- `docs/debugging/`：已确认故障的根因与修复记录 SSOT。
- 外部协作系统：排期、负责人和协作状态 SSOT；registry 仅保留链接与同步时间。

## 1. 收集事实

先声明分析范围、时间窗、版本和对比基线，再读取数据。优先使用结构化、可重复查询的数据源：

| 数据源 | 能回答的问题 | 最低质量检查 |
|--------|--------------|--------------|
| telemetry 事件/会话 | 热点命令、成功率、错误类别、重试序列、Agent 差异 | 覆盖率、session 关联率、unknown 错误占比、版本分布 |
| 审计/日志/trace/metrics | 失败上下文、真实根因、性能与稳定性 | 时间对齐、抽样可回溯、敏感信息脱敏 |
| debugging registry | 已知根因、复发问题、观测盲区 | 同质症状去重、结论是否仍有效 |
| 需求/缺陷系统、用户反馈 | 已知诉求、优先级背景、重复工作项 | 项目范围正确、链接可访问、状态新鲜 |
| 测试/发布记录 | 回归、版本切换与修复落点 | 与分析版本和时间窗一致 |

先扫描项目现有的可观测性文档、脚本、CLI 和外部协作工具，确定每类事实的权威读取入口。优先复用项目已有的结构化查询能力；若项目没有 telemetry、会话关联或工作项系统，就使用实际存在的数据源并在报告中说明覆盖边界，不为套用本流程而臆造命令或基础设施。

无论使用哪种工具，都只把支撑结论所需的脱敏摘要写入报告，不直接复制用户输入、凭证、完整转录或其他敏感原始内容。

### 工具映射示例：aw-debug

以下仅演示如何把一个项目已有的工具映射到本流程，不是 harness 的通用依赖：

| 进化步骤 | aw-debug 项目中的可用入口 |
|----------|---------------------------|
| 基本统计 | `aw-debug --ni telemetry stats -t <window> --json` |
| 会话模式分析 | `aw-debug --ni telemetry stats --by session -t <window>`、`aw-debug --ni telemetry session <id>` |
| 失败抽样验证 | 根据 telemetry 事件标识读取对应的本地 audit 记录 |
| 外部工作项去重 | `aw-debug --ni doc tapd query/search/show ...` |

迁移到其他项目时，应把右列替换为该项目真实存在的日志平台、指标系统、分析脚本和协作系统入口；左列的事实目标与质量检查保持不变。

若关键字段缺失、样本太少或窗口混入重大版本迁移，把限制写进报告并降低置信度；数据不足时允许本轮只有“补观测”候选项，不强行产出产品需求。

## 2. 分析并形成报告

应用 [进化分析模板](../templates/evolution-report.md)。分析顺序固定为：

1. 建立总量、成功率、耗时、活跃会话等基线，并按版本、调用方、命令或场景分层，避免聚合值掩盖差异。
2. 检测重复失败、失败后换参数、长尾耗时、能力未使用、人工绕路和跨会话复发等模式。
3. 回到审计/日志/排障记录抽样验证。相关性不是根因；报告必须区分事实、推断和待确认假设。
4. 将发现归为：产品缺陷、能力需求、skill/文档问题、可观测性缺口、无需处理的正常现象。
5. 每个建议定义影响范围、置信度、建议动作、成功指标和验证窗口。

每条发现使用稳定 ID：`EVO-<YYYYMMDD>-NN`。同一根因只保留一个候选项，其他报告通过 evidence 链接追加证据。

### 证据门槛

候选项至少满足以下一项才可进入 accepted：

- 可稳定复现的单次严重故障；
- 同类模式跨两个及以上独立会话出现；
- 有明确基线的显著退化；
- 用户明确反馈且能关联到可观察事实。

严重度高但证据不足时标 `candidate` 并优先补观测。`unknown` 错误占比高通常先路由为可观测性缺口，而不是猜测产品根因。

## 3. 路由与处理

先查 `docs/evolution/registry.md`、`docs/debugging/registry.md`、`docs/design/`，再查询外部协作系统，避免重复创建。

| 类型 | 路由 | 创建前必须具备 |
|------|------|----------------|
| 已实现行为偏离 spec / 稳定复现异常 | bug + debugging record + 回归 eval | 复现/证据、期望与实际、影响、可程序化的验收标准 |
| 新能力或行为变化 | requirement + design spec + 目标 eval | 用户价值、范围/非目标、形式化验证目标（L1/L2/L3）、运行期指标与验证命令 |
| Agent 调用姿势或决策路径不佳 | skill/doc change + L2 评测用例 | 失败模式、目标行为、可复跑的 skill/Agent 评测场景 |
| 无法判断问题类别或效果 | observability task | 缺失信号、采集边界、补齐后的可复跑判定方法 |
| 正常现象、样本噪声、已有项 | dismiss / merge | 理由及被合并目标链接 |

创建外部工作项是有副作用的动作：先给出草稿与去重结果，由用户确认后再写入。若当前集成只支持查询/评论而不支持创建，保留草稿并将 registry 状态置为 `accepted`，不要声称已经创建。

工作项草稿应用 [进化工作项模板](../templates/evolution-work-item.md)，最少包含：背景、证据链接、影响、范围与非目标、程序化验收标准（含需沉淀的 `evals/` 回归用例）、成功指标、可复跑验证命令与验证窗口。创建成功后只在 registry 登记外部链接，不把外部状态全文同步回仓库。

## 4. 实施后验证并继续循环

进化循环与 [evaluation.md](evaluation.md) 形成双向闭环：
- **线上 → 离线回流**：所有路由为 `bug`、`requirement` 或 `skill` 的候选项，实施完成（进入 `implemented`）前必须把对应的失败模式或目标契约沉淀为可复跑的离线验证用例（`evals/`），并在 registry 中登记路径；无法离线复现的须显式说明原因。
- **离线 → 线上延续**：`docs/design/` 中标记为「运行期延续验证」的目标，以及本轮进化工作项的线上效果验证，均在此阶段跟踪。

处理候选项时，在实施前登记 baseline、target、观察窗口、生效版本以及**可重复执行的验证命令或脚本路径**（如 `evals/runtime/<name>.*` 或项目既有结构化查询命令）。没有预先定义成功指标和可复跑口径的改进不能进入 `validating`。

验证时直接执行预先登记的同一验证命令/脚本对比基线，杜绝人工口述口径漂移：

- 达到目标且无明显副作用：`validated`。
- 指标未改善或变差：`ineffective`，保留证据并决定回滚、重做或拆分新候选项。
- 样本不足、版本覆盖不足或数据质量不合格：`inconclusive`，延长窗口，不宣称成功。

验证结论写入新周期报告，并更新 registry。已验证项仍保留，供以后识别复发；下一周期从上次窗口结束处继续，避免重叠计数。

## 状态机与恢复

```text
observed -> candidate -> accepted -> planned -> implemented -> validating
               |           |                                  |   |   |
               +-> merged   +-> dismissed              validated ineffective inconclusive
```

- `observed`：报告中首次发现，尚未完成去重/证据审查。
- `candidate`：证据不足或待人工决策。
- `accepted`：确认值得处理，尚未进入外部计划。
- `planned`：已有 spec/工作项及负责人或排期。
- `implemented`：变更已交付但尚未跨验证窗口。
- `validating`：已进入观察窗口。
- 终态为 `validated`、`ineffective`、`dismissed`、`merged`；`inconclusive` 可在补足数据后回到 validating。

每完成一个阶段立即更新 registry 的状态、时间、证据/产物链接。中断后先读取 registry，从最早的非终态项恢复；报告文件是否存在且包含数据范围与发现表，是分析阶段的完成判据；外部链接可访问是 planned 的完成判据；验证查询与基线同口径且结果已落报告，是验证阶段的完成判据。

重复执行必须幂等：报告文件名相同则先检查，不覆盖；候选项按“归一化问题 + 影响对象”去重；外部项先搜索再创建；验证按候选 ID 与窗口去重。
